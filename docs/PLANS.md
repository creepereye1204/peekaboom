## 순서의 논리

```
리스크가 큰 것부터 → 재미의 핵심 → 완성도 → 범위 확장
```

흔한 실패 패턴은 반대로 가는 것이다: 예쁜 메뉴와 캐릭터 애니메이션을 먼저 만들고, 마지막에 "어? 모바일에서 연결이 안 되네"를 발견한다.

그래서 **M1에서 못생긴 사각형 두 개로 실제 폰 연결을 검증한다.** 여기서 막히면 설계를 바꿀 시간이 있다.

---

## 각 마일스톤의 "실패 조건"

성공 기준만큼 실패 기준이 중요하다. 이걸 넘으면 **멈추고 설계를 다시 연다.**

| M | 실패 조건 | 그때 할 일 |
|---|---|---|
| M1 | 한국 주요 통신망 조합 중 절반 이상에서 P2P 연결 실패 | TURN 없이 불가능하다는 뜻. 프로젝트 전제(CB-1) 재검토 |
| M2 | 플레이테스트에서 "긴장감 없다"가 다수 | 소음 대신 다른 정보 채널 설계 (시각적 단서?) |
| M2 | 가시성 필터링으로 인기척이 너무 적어 술래가 답답함 | 정보량 튜닝. 필터링 자체는 포기 불가 |
| M3 | 중급 안드로이드에서 30fps도 안 나옴 | 렌더링 예산 재설계. 1비트 아트로 전환 |
| M4 | 8명에서 대역폭/CPU 한계 | 최대 인원 6명으로 축소 |

## 하지 않기로 한 것

`PRODUCT_SENSE.md`의 "하지 않는 것" 목록 참조. 요약: 랭킹, 무기, 9명+, 커스터마이징, 봇, 수익화.

**이것들은 "나중에"가 아니라 "안 함"이다.** 나중에 하려면 CB-1을 깨야 하고, 그러면 다른 프로젝트가 된다.
