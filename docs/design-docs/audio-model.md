# DD-008 · 오디오 모델 (소음이 곧 게임플레이)

- 상태: **제안됨** — PRODUCT_SENSE G1이 검증되기 전까지 확정하지 않는다
- 관련: CB-3, DD-002, PRODUCT_SENSE G1

---

## 문제

우리 게임에서 소리는 분위기가 아니라 **주된 정보 채널**이다.

DD-002 때문에 술래는 숨은 사람의 좌표를 받지 못한다. 시야 원뿔 안에 들어오기 전까지 술래가 가진 정보는 소음뿐이다. 즉 **오디오가 없으면 술래가 아무 단서도 없다.**

동시에 이건 프로젝트 최대의 제품 도박이다. PRODUCT_SENSE G1("소리가 시각보다 긴장감을 만든다")이 틀리면 게임의 절반을 다시 설계해야 한다.

그래서 이 문서는 **확정이 아니라 검증 대상**으로 쓴다.

---

## 두 층으로 나눈다

소리를 하나로 뭉뚱그리면 안 된다. 성격이 다른 두 개다.

| 층 | 무엇 | 누가 결정 | 왜 분리하나 |
|---|---|---|---|
| **정보층** | 소음 이벤트 (누가, 어느 방향, 얼마나 큰) | **호스트** (`sim`) | 게임 규칙이다. 결정적이어야 하고, 가시성 필터를 거쳐야 한다 |
| **표현층** | 실제 재생되는 파형, 볼륨, 팬, 리버브 | 클라이언트 | 게임 결과에 영향을 주지 않는다. 브라우저마다 달라도 된다 |

**정보층이 표현층을 통해 새면 안 된다.** 예: 볼륨을 거리에 정확히 비례시키면, 클라이언트가 볼륨을 역산해 거리를 알아낸다. 그건 좌표 유출이다(DD-002).

---

## 정보층 규칙

`sim`이 소음 이벤트를 만든다. 호스트가 피어별로 필터링해 보낸다.

```
NoiseHint {
    direction_q8: u8,   // 0..255 = 0..2π. 수신자 기준 방향
    strength: u8,       // 0..3 (약/중/강/지속)
}
```

**거리를 보내지 않는다.** 방향과 강도뿐이다.

| 행동 | 들리는 반경 | 강도 |
|---|---|---|
| 걷기 | 7타일 | 약 |
| 살금살금 | 0 | — |
| 대시 | 14타일 | 강 |
| 빙의/해제 | 4타일 | 약 |
| 탈출구 개방 | 16타일, 지속 | 지속 |
| 유령 쿵 | 10타일 | 중 |

### 왜 강도를 3단계로만 주는가

연속값을 주면 그게 거리 정보가 된다. 3~4단계면 "가까운지 먼지" 감은 오되 삼각측량은 안 된다.

### 방향 양자화

`direction_q8`은 256단계 = 1.4° 해상도. 이건 충분히 정밀한데, **거리가 없으므로 방향만으로는 위치를 특정할 수 없다.** 두 번의 소음을 삼각측량하려면 그사이 소음원이 안 움직여야 하는데, 움직이니까 소리가 난 것이다.

### 유령 쿵이 진짜 발소리와 구분되지 않는 것

이건 버그가 아니라 설계다(product-specs/hide-and-seek.md). 유령에게 **"교란"**이라는 실질적 영향력을 주는 유일한 수단이고, 술래 입장에서는 "이 소리를 믿을 수 있나"라는 판단이 추가된다.

따라서 `NoiseHint`에 소음원의 종류를 넣지 않는다. 술래는 방향과 강도만 받는다.

## 표현층 설계

### 공간화

WebAudio `PannerNode`, `panningModel: 'equalpower'`.

- 2D 게임이므로 HRTF는 과하다. `equalpower`가 싸고 충분하다
- 리스너는 로컬 플레이어 위치, 오리엔테이션은 `facing`
- **주의**: 정보층이 방향만 주므로, 표현층은 "방향 × 고정 거리"에 소리를 놓는다. 실제 거리를 모르기 때문이다

즉 술래 클라이언트는 이렇게 재생한다:

```
소음원 가상 위치 = 리스너 위치 + 방향벡터 × (강도로 정한 고정 거리)
강도 약 → 6타일, 중 → 4타일, 강 → 2타일
```

**거리를 강도로부터 역산하는 셈인데, 그 역산은 3단계 해상도밖에 안 된다.** 이게 의도한 정보량이다.

### 화면 가장자리 화살표

소리만으로는 부족하다:

- 음소거하고 하는 사람이 있다
- 이어폰 없이 폰 스피커면 방향감이 거의 없다
- 청각 접근성

그래서 **소음은 항상 시각적으로도 표시된다** (화면 가장자리 화살표, product-specs/mobile-controls.md). 소리는 보조가 아니라 병렬 채널이다.

> 이게 G1 검증을 까다롭게 만든다: 화살표가 있으면 소리가 없어도 게임이 되는 것 아닌가? 검증 실험은 **화살표를 끈 조건**과 **소리를 끈 조건**을 따로 비교해야 한다.

### BGM

**없다.** 정적이 긴장을 만든다. 로비에만 조용한 루프 하나.

### 모바일 자동재생

첫 `pointerdown`에서 `AudioContext.resume()`. 실패해도 게임은 진행된다(화살표가 있으므로).

## G1 검증 실험 (exec-plan 002)

4명 이상, 3가지 조건으로 각 3라운드:

| 조건 | 소리 | 화살표 |
|---|---|---|
| A (기준) | 켬 | 켬 |
| B | **끔** | 켬 |
| C | 켬 | **끔** |

측정:

- 술래가 첫 발견까지 걸린 시간
- 라운드당 "어디 있는지 전혀 모르겠다" 발화 횟수 (관찰 기록)
- 플레이어 주관 평가: "긴장됐다" 1~5

가설이 맞다면 **B에서 긴장감이 뚜렷이 떨어져야 한다.** B와 A가 비슷하면 소리는 장식이고, 정보층 설계를 시각 중심으로 다시 짜야 한다.

C(화살표 끔)가 A보다 재밌다면 — 그것도 유의미한 발견이다. 화살표를 옵션으로 내리고 소리를 주 채널로 승격한다.

## 에셋 상황 (TD-004)

**게임플레이 SFX가 아직 없다.** Kenney *Interface Sounds*는 UI 전용이고 발소리·대시·잡힘이 없다.

필요 목록:

| 소리 | 길이 | 비고 |
|---|---|---|
| 발소리 (걷기) | 0.2초 × 4종 변형 | 변형이 없으면 기계적으로 들린다 |
| 발소리 (살금살금) | — | **재생하지 않는다** (소음 0) |
| 대시 | 0.4초 | 저역 강조 |
| 빙의 / 해제 | 0.25초 | 짧고 건조하게 |
| 탈출구 개방 | 루프 2초 | 점점 커짐 |
| 잡힘 | 0.6초 | 정적 0.2초 후 임팩트 |
| 유령 쿵 | 0.3초 | **발소리와 구분되면 안 된다** |

출처 후보: freesound.org CC0 필터, Kenney *Impact Sounds* / *RPG Audio*.
**아직 실제로 받아 확인하지 않았다.**

예산: OGG Vorbis 64kbps 모노, 전체 ≤ 120 KB (FRONTEND.md §3).
