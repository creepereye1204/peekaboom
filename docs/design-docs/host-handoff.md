# DD-007 · 호스트 이양

- 상태: **채택됨 (타협 포함)**
- 관련: DD-002, CB-3, RELIABILITY §3, TD-005

---

## 문제

호스트 하나가 유일한 진실을 갖는 구조(DD-002)에서 **호스트가 나가면 게임이 죽는다.**

그리고 호스트 이탈은 예외가 아니라 일상이다. 탭을 닫고, 전화가 오고, 지하철에 들어가고, 배터리가 나간다. 6명이 20분 플레이하면 최소 한 번은 일어난다고 봐야 한다.

여기에 DD-002와의 긴장이 있다: **이양을 매끄럽게 하려면 후보 호스트가 미리 월드 상태를 알아야 하는데, 월드 상태는 곧 숨은 사람의 좌표다.**

이 문서는 그 긴장을 어떻게 타협했는지 기록한다.

---

## 결정 1 · 선출: 사전순 최소값

```
새 호스트 = 남아있는 피어 중 selfId 사전순 최소값 (자신 포함)
```

- 투표 없음, 합의 프로토콜 없음, 네트워크 왕복 0회
- `selfId`는 Trystero가 주는 전역 고유 문자열이라 동점이 없다
- 모든 피어가 같은 목록을 보고 **같은 답을 낸다** — 그게 핵심이다

### 왜 합의 알고리즘을 안 쓰나

Raft/Paxos류는 "누가 리더인지 모두가 동의하게" 만드는 문제를 푼다. 우리는 그 문제가 없다. 피어 목록이 로컬에 있고, 결정 함수가 순수 함수이므로 동의는 공짜다.

분할(split-brain)은 어떤가? WebRTC 풀메시에서 A-B는 연결됐는데 A-C는 끊긴 상황은 가능하다. 이때 A와 C가 서로 다른 호스트를 뽑을 수 있다.

**우리는 이걸 풀지 않는다.** 8명짜리 파티 게임에서 부분 분할은 드물고, 발생하면 두 그룹이 각자 게임을 이어간다. 랭킹도 영구 상태도 없으므로 피해가 "라운드가 이상해진다" 수준이다. 정직하게 리스크로 기록하고 넘어간다.

---

## 결정 2 · 상태 복구: HostShadow

새 호스트는 무엇으로부터 시뮬레이션을 재개하는가?

### 순진한 방법과 그 한계

"각 클라이언트가 마지막 스냅샷을 갖고 있으니 그걸로 복원하면 된다."

**안 된다.** DD-002 때문에 각 클라이언트가 받은 스냅샷은 **자기 시야 안의 것뿐**이다. 새 호스트가 그걸로 복원하면 시야 밖의 플레이어들이 전부 사라진다.

### 채택한 방법

호스트는 **후보 호스트 한 명에게만** `HostShadow` 패킷을 2초마다 보낸다.

- 수신자: 자신을 제외한 피어 중 사전순 최소값 (= 자기 다음 호스트)
- 내용: 전체 월드 상태를 **4타일 단위로 양자화**한 저해상도 스냅샷
- 채널: 신뢰성(reliable). 이건 반드시 도착해야 한다

```
0x06 HostShadow
  u32 tick
  u8  entity_count
  [ u8 id | u8 x_coarse(0..31) | u8 y_coarse | u8 state ]
```

8명 기준 **약 37바이트**, 2초 주기 → 0.02 KB/s. 무시할 수 있는 비용이다.

### 이양 절차

```
1. onPeerLeave(호스트) 감지
2. 모든 피어가 독립적으로 새 호스트를 계산 (같은 답)
3. 새 호스트: 가진 HostShadow로 World 복원
4. 새 호스트: 자기 예측 버퍼의 미확인 입력 재적용
5. 새 호스트: HostHandoff{new_host, resume_tick} 브로드캐스트 (reliable)
6. 나머지: resume_tick으로 되감고 재개
7. 이후 몇 틱에 걸쳐 정밀도가 회복된다
```

되감기 손실은 최대 2틱(약 66ms) + Shadow 주기(최대 2초)만큼의 위치 오차.

**오차는 빠르게 사라진다.** 새 호스트가 첫 틱을 돌리면 그때부터 정상 스냅샷이 나가고, 클라이언트들은 자기 예측을 재조정한다(DD-003). 사용자가 보는 건 "잠깐 캐릭터들이 살짝 튀는" 정도다.

## 받아들인 타협 (TD-005)

**후보 호스트는 4타일 정밀도로 모두의 위치를 안다.**

개조 클라이언트를 만들면 술래가 아닌데도 "저 사람이 대충 어느 방에 있다"를 알 수 있다.

### 왜 이걸 받아들이는가

| 선택지 | 문제 |
|---|---|
| Shadow를 안 보낸다 | 호스트 이탈 = 게임 종료. **일상적으로 일어나는 일이라 치명적** |
| Shadow를 정밀하게 보낸다 | 후보 호스트가 완전한 월핵 |
| Shadow를 암호화해 봉인 | 복호화 키를 결국 그 피어가 가져야 하므로 의미 없음 |
| 모든 피어에게 조각내어 분산 (비밀 분산) | 이양 시 조각을 모아야 하는데, 호스트가 나간 직후가 가장 불안정한 시점이다. 복잡도 대비 이득 없음 |
| **4타일 양자화 Shadow** ← 채택 | 방 단위 위치만 노출 |

4타일은 우리 맵에서 **방 하나 크기**다. "어느 방에 있다"는 알아도 "어디 숨었다"는 모른다. 숨바꼭질에서 방을 좁히는 건 술래가 어차피 하는 일이고, 정확한 은신처를 찾는 게 게임의 본체다.

### 재검토 트리거

플레이테스트에서 **이걸 악용한 사례가 실제로 나오면** 다시 연다. 그전까지는 "일어날 수 있는 일"에 복잡도를 지불하지 않는다.

## 호스트가 아닌 피어의 이탈

훨씬 단순하다 (RELIABILITY §4):

```
0.3초  → "연결 불안정" 아이콘
3초    → 캐릭터 정지. 무적 아님
10초   → 유령 처리, 라운드에서 제외
```

**3~10초 사이에 무적을 주지 않는 이유**: 일부러 연결을 끊어 무적이 되는 치트가 생긴다. 끊긴 쪽이 손해 보는 게 맞다.

---

## 테스트 요구사항

이 기능은 **수동으로 테스트하기가 매우 어렵다**(호스트 브라우저를 정확한 타이밍에 죽여야 한다). 그래서 `tests/netsim.rs`의 가상 전송 계층에서 검증한다:

- [ ] 호스트를 임의 틱에 제거 → 남은 피어들이 같은 새 호스트를 뽑는다
- [ ] 이양 후 100틱 진행 → 모든 피어의 상태 해시가 수렴한다
- [ ] 이양 직후 위치 오차가 4타일 이하, 30틱 내에 0.5타일 이하로 수렴
- [ ] 호스트가 연속 2번 나가도 동작한다 (Shadow 수신자가 호스트가 된 직후 또 나가는 경우)
- [ ] Shadow를 한 번도 못 받은 피어가 호스트가 되는 경우 → 자기 스냅샷으로 폴백하고, 보이지 않던 플레이어는 **마지막 알려진 위치**에 둔다 (사라지게 하지 않는다)

마지막 항목이 중요하다. Shadow 수신자가 먼저 나가면 이 경우가 실제로 생긴다.

## 미결

- [ ] Shadow 주기 2초가 적절한지. 짧으면 오차가 작고 노출이 커진다. 실측 후 조정
- [ ] 분할 발생 빈도. M1 연결 매트릭스에서 관찰 가능하면 기록
- [ ] 호스트가 "나 나갈게"를 예고하고 나가는 경우(탭 닫기 전 `beforeunload`) 우아한 이양이 가능한지. 브라우저가 시간을 얼마나 주는지 실측 필요
