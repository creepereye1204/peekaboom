# DD-005 · 입력 추상화 (InputIntent)

- 상태: **채택됨**
- 관련: H6, CB-4

---

## 문제

같은 게임을 키보드, 터치, 게임패드로 조작한다. 각 경로가 게임 로직까지 뚫고 들어오면 로직이 세 벌이 된다. 그리고 네트워크로 보내야 하는 건 "W키를 눌렀다"가 아니라 "위로 가려 한다"이다.

## 결정

**모든 입력은 `InputIntent` 하나로 수렴한다.** `sim`은 입력 장치를 모른다.

```rust
#[derive(Clone, Copy, PartialEq, Eq)]
pub struct InputIntent {
    /// 이동 방향. 길이 0 또는 정규화(≈1.0). Q8.8 고정소수점
    pub move_dir: Vec2Fixed,
    /// 비트플래그: INTERACT | DASH | EMOTE_1..4
    pub action: ActionFlags,
    /// 조준 방향 (술래의 손전등 등). None이면 이동 방향을 따름
    pub look: Option<Vec2Fixed>,
}
```

크기: 이동 4B + 액션 1B + 조준 4B+1B = **10바이트**. 네트워크로 그대로 보낸다.

### 왜 `look`이 Option인가

키보드+마우스는 이동과 조준이 분리된다. 터치는 기본적으로 진행 방향을 본다(조이스틱 하나). 게임 로직이 "조준이 따로 있으면 그걸, 없으면 이동 방향을" 쓰도록 하면 두 조작계가 같은 코드로 돌아간다.

## 장치별 매핑

### 키보드

| 입력 | 결과 |
|---|---|
| WASD / 방향키 | `move_dir` (대각선은 정규화) |
| Space / E | `INTERACT` |
| Shift | `DASH` |
| 1~4 | `EMOTE_n` |
| 마우스 위치 | `look` = 플레이어→커서 방향 |

### 터치 (모바일)

**가상 조이스틱 1개 + 액션 버튼 2개.** 화면 오른쪽에 조이스틱을 둘지 왼쪽에 둘지는 설정에서 바꾼다(왼손잡이).

```
┌──────────────────────────────┐
│                       [소음] │   ← 상단 우: 미니맵/상태
│                              │
│                              │
│                              │
│   ○                    (E)   │   ← 조이스틱      액션
│  ◉ ●                  (대시) │
│   ○                          │
└──────────────────────────────┘
```

조이스틱 규칙:

- **고정 위치가 아니라 "터치 시작 지점이 중심"**이 된다 (floating stick). 폰 크기·손 크기 편차를 흡수한다
- 데드존 12% — 손가락 미세 떨림 무시
- 최대 반경 64 CSS px. 그 밖으로 끌면 방향만 갱신, 크기는 1.0 고정
- 조이스틱 시각 요소는 Kenney *Onscreen Controls* 에셋 사용 (asset-manifest 참조)

액션 버튼:

- 최소 터치 타겟 **48×48 CSS px** (접근성 가이드라인)
- 화면 하단 가장자리에서 16px 이상 띄운다 (iOS 홈 인디케이터 영역 회피)

### 게임패드

Gamepad API. 왼쪽 스틱 → `move_dir`, 오른쪽 스틱 → `look`, A → `INTERACT`, RT → `DASH`. 연결되면 자동 감지하고 터치 UI를 숨긴다.

## 모바일 특수 처리

이건 "나중에"가 아니라 처음부터 들어간다 (CB-4).

| 문제 | 처리 |
|---|---|
| 스크롤/줌 제스처가 조작을 먹음 | 캔버스에 `touch-action: none`, `preventDefault` |
| 더블탭 확대 | `<meta name="viewport" content="... user-scalable=no, viewport-fit=cover">` |
| 노치/홈바 | CSS `env(safe-area-inset-*)`로 UI 패딩 |
| 세로↔가로 회전 | 레이아웃 재계산 + 캔버스 리사이즈. **게임은 안 멈춘다** |
| 화면 꺼짐 | `navigator.wakeLock.request('screen')` — 실패해도 조용히 넘어감 |
| 오디오 자동재생 차단 | 첫 터치에서 `AudioContext.resume()` |
| 멀티터치 | 포인터 ID로 조이스틱/버튼 소유권 추적. 손가락 3개여도 안 꼬임 |
| 백그라운드 전환 | `visibilitychange` → 입력 전송 중단, 스냅샷은 계속 수신. 복귀 시 강제 동기화 |

### 세로 모드

세로에서도 플레이 가능하되, 카메라 시야가 좁아진다. 이걸 **게임적으로 인정한다**: 가로가 유리하다는 걸 숨기지 않고, 첫 실행 시 "가로로 돌리면 더 잘 보여요" 한 번만 안내한다. 강제하지 않는다.

## 테스트 가능성

`InputIntent`가 순수 데이터라서 `sim` 테스트는 입력 시퀀스를 직접 만들면 된다.

```rust
#[test]
fn 대각선_이동은_정규화된다() {
    let i = keyboard_map(&[Key::W, Key::D]);
    assert!((i.move_dir.len() - Fixed::ONE).abs() < Fixed::from_f32(0.01));
}
```

장치 레이어(`crates/input`)는 브라우저 이벤트를 `InputIntent`로 바꾸는 순수 함수들의 모음이어야 한다. DOM을 직접 만지는 부분은 얇은 껍데기로 분리해서 테스트에서 제외한다.
