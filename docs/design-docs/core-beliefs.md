# Core Beliefs

이 프로젝트의 모든 기술 결정이 딛고 선 전제들. 여기 적힌 믿음과 충돌하는 제안은 믿음 자체를 먼저 반박해야 한다.

---

## CB-1. 서버가 없다는 건 제약이 아니라 제품 특성이다

서버비 0원은 "돈이 없어서"가 아니다. 서버가 없으면:

- 배포가 `git push`다. 롤백도 `git revert`다.
- 운영 사고가 존재할 수 없다. 새벽에 깨질 일이 없다.
- 개인정보를 저장할 곳이 없으니 GDPR/개인정보보호법 표면적이 0이다.
- 프로젝트가 5년 방치돼도 계속 돌아간다.

그래서 "서버 하나만 두면 쉬운데요"라는 제안은 대부분 **문제를 푸는 게 아니라 옮기는 것**이다. 정말 필요하면 CB-1을 반박하는 문서를 먼저 써라.

## CB-2. 지연(latency)은 숨기는 것이지 없애는 게 아니다

P2P에서 RTT 40~120ms는 정상이다. 목표는 "지연 0"이 아니라 **지연이 느껴지지 않는 것**이다.

- 로컬 플레이어 이동은 **항상 즉시** 반응한다 (클라이언트 예측)
- 원격 플레이어는 100ms 과거를 보간해서 부드럽게 보여준다
- 결과(잡힘/못 잡힘)는 호스트가 정한다 — 화면과 어긋나면 화면이 양보한다

"내 화면에선 분명 잡았는데"는 받아들이는 비용이다. 대신 **잡는 판정 반경을 넉넉히** 줘서 그 순간이 드물게 만든다.

## CB-3. 숨은 사람의 위치는 비밀이어야 게임이 성립한다

숨바꼭질에서 위치가 새면 게임 자체가 없다. 그런데 P2P 브로드캐스트는 기본적으로 모두에게 모든 걸 보낸다. 브라우저 개발자도구만 열면 좌표가 보인다.

그래서 **호스트가 피어별로 가시성을 필터링**한다. 이건 최적화가 아니라 **게임 규칙의 일부**다. 대역폭을 아끼려고 하는 게 아니다.

## CB-4. 모바일은 포팅 대상이 아니라 1차 타겟이다

"링크 보내서 같이 하는 게임"의 대부분은 폰에서 열린다. 따라서:

- 터치 조작이 키보드의 열화판이면 실패다. 별도로 설계한다.
- 세로 모드에서도 플레이 가능해야 한다.
- 로딩 3초 넘으면 사람들은 그냥 나간다. 번들 크기는 기능이다.
- 발열/배터리 때문에 60fps를 항상 쫓지 않는다. 30fps 고정이 더 나을 때가 많다.

## CB-5. 공개 인프라는 언젠가 죽는다

Nostr 릴레이, MQTT 브로커, BitTorrent 트래커 — 전부 남의 것이고 공짜고 보장이 없다. 어느 날 조용히 죽는다.

따라서 **시그널링은 다중화하고, 최후에는 사람이 직접 코드를 붙여넣는 경로를 항상 남긴다.** 우아하지 않아도 된다. 동작하기만 하면 된다.

## CB-6. 결정적 시뮬레이션은 선택이 아니라 기반이다

`sim`이 결정적이면:

- 호스트 이양 시 새 호스트가 같은 상태를 재현할 수 있다
- 리플레이가 입력 로그만으로 저장된다 (용량 극소)
- 버그 재현이 "이 입력 시퀀스"로 끝난다
- 델타 압축이 쉬워진다

부동소수점을 포기하고 고정소수점을 쓰는 비용은 이 넷에 비하면 싸다.

## CB-7. 문서가 틀렸으면 코드가 아니라 문서를 고친다

코드는 여러 사람이/여러 세션이 짠다. 코드만 보면 "왜 이렇게 했는지"가 사라진다. 문서가 사양이고, 구현이 문서와 어긋나면 **둘 중 하나가 버그**다. 어느 쪽인지 정하고 고친다. 방치하지 않는다.

## CB-8. 재미없으면 기술적으로 아무리 훌륭해도 실패다

네트코드가 완벽해도 숨을 곳이 뻔하면 지루하다. 제품 판단은 `docs/PRODUCT_SENSE.md`에 있고, 그게 기술 판단보다 위에 있다.
