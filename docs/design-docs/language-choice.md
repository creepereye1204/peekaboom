# DD-001 · 언어 선택 (Rust + WASM vs 순수 JS/TS)

- 상태: **채택됨 (조건부)** — 아래 "탈출 조건"을 만족하면 재검토한다
- 관련: CB-6, CB-4, H5, DD-003, DD-007

> 이 문서는 뒤늦게 작성됐다. 결정은 프로젝트 시작 시점에 내려졌지만 근거가 기록되지 않아
> "왜 WASM인가"라는 질문이 나중에 다시 나왔다. **기록되지 않은 결정은 결정이 아니다** (CB-7).

---

## 문제

브라우저 2D 멀티플레이 게임을 무엇으로 만들 것인가.

후보: 순수 JS/TS, Rust → WASM, C++ → WASM.

---

## 정직한 계산

### Rust/WASM이 실제로 버는 것

**결정적 시뮬레이션 — 이것 하나다.**

JS는 모든 숫자가 f64다. 고정소수점을 쓰려면 `| 0`, `Math.imul()`, `>>> 0`을 **한 군데도 빠뜨리지 않고** 발라야 한다. 한 곳만 새도 f64 연산이 섞이고, 그건 조용히 동작하다가 어느 날 두 피어의 상태가 갈린다.

Rust는 `i32` 연산이 기본이고, `Fx(i32)` 뉴타입으로 감싸면 `f32`가 섞이는 순간 **컴파일 에러**다. 타입 시스템이 규율을 대신 지켜준다.

그리고 결정성 위에 세 가지가 올라가 있다:

| 기능 | 결정성 의존 |
|---|---|
| 호스트 이양 (DD-007) | 새 호스트가 같은 상태를 재현해야 한다 |
| 클라이언트 재조정 (DD-003) | 미확인 입력 재실행이 정확히 맞아떨어져야 한다 |
| 리플레이 | 입력 로그만으로 재생 |

**결정성이 깨지면 이 셋이 동시에 무너진다.** 도미노의 첫 조각이라 보호 가치가 크다.

### Rust/WASM이 못 버는 것

- **성능**: 8명 × 30Hz 시뮬레이션은 JS로도 한참 여유롭다. 실제 병목은 **GPU 드로우콜과 네트워크**이지 CPU 연산이 아니다. "Rust라서 빠르다"는 이 프로젝트에서 거짓말에 가깝다
- **렌더링**: WebGL2 호출은 어차피 JS 경계를 넘는다. `web-sys` 바인딩을 거치는 만큼 오히려 약간 느리다
- **네트워크**: Trystero가 JS라 패킷마다 경계를 왕복한다

### 실제 비용

| 항목 | JS/TS | Rust/WASM |
|---|---|---|
| 번들 (gzip) | ~50 KB | ~100–150 KB (추정, 미측정) |
| 툴체인 | node 하나 | node + rust + wasm-bindgen CLI |
| 빌드 함정 | 적음 | wasm-bindgen CLI ↔ 크레이트 버전 정확히 일치 필요 |
| 반복 속도 | 핫리로드 즉시 | 컴파일 대기 |
| 로직 테스트 | 브라우저/jsdom | **네이티브, 매우 빠름** |

번들 차이 50~100KB는 1.5MB 예산(H5) 안에서는 여유롭지만, CB-4(로딩 3초)에 불리한 건 사실이다.

## 결정

**Rust + wasm-bindgen.** 단, 위 계산을 인정한 채로 선택한다.

결정 요인 순서:

1. **결정성을 타입으로 강제할 수 있다** — 이게 유일하게 대체 불가능한 이득
2. **로직이 네이티브에서 테스트된다** — `sim`/`net`/`input`이 브라우저 없이 `cargo test`로 돈다. 이 워크플로가 개발 속도를 실제로 올린다
3. **포트폴리오 가치** — 이 프로젝트의 목적 중 하나다 (PRODUCT_SENSE). 결정적 시뮬 + 권위 서버 + 예측/재조정을 Rust로 구현한 사례는 설명거리가 된다

**"성능 때문에"는 근거가 아니다.** 그렇게 적혀 있으면 틀린 것이다.

### 왜 C++가 아닌가

초기에 채용 시장을 이유로 잠깐 고려했다가 접었다.

- Emscripten 툴체인이 wasm-bindgen보다 JS 상호운용이 번거롭다
- 메모리 안전성을 수동으로 관리해야 하고, 그 비용이 얻는 것보다 크다
- `unsafe` 금지(H8)라는 우리 규율이 C++에서는 의미가 없다

### 왜 macroquad/Bevy가 아닌가

엔진 선택은 별개 문제다. DD-004 참조. 요약: Trystero(JS)를 반드시 불러야 하는데 macroquad는 wasm-bindgen을 쓰지 않아 JS 심을 직접 써야 하고, Bevy는 번들이 무겁다.

## 조건부인 이유 · 탈출 조건

이 결정은 **되돌릴 수 있게** 유지한다. 다음 중 하나가 관측되면 재검토한다:

| 조건 | 왜 |
|---|---|
| WASM gzip이 400 KB를 넘는다 | 번들 이득 없이 복잡도만 지고 있다는 뜻 |
| 모바일 초기 로딩이 계속 4초를 넘고 원인이 WASM 다운로드/인스턴스화다 | CB-4 위반. 게임의 훅이 첫 5분에 있다 |
| JS↔WASM 경계 왕복이 프로파일에서 상위 병목으로 잡힌다 | 구조가 틀렸다는 신호 |
| 빌드 파이프라인 문제로 개발이 자주 멈춘다 | 도구가 일을 방해하면 도구를 바꾼다 |

측정은 exec-plan 003에서 한다.

### 재검토 시 이전 비용

`sim`/`net`/`input`이 브라우저 의존 없이 짜여 있으므로(DD-006), JS로 옮긴다면 **이 세 크레이트를 TS로 포팅**하면 된다. 고정소수점은 `Fx` 타입을 클래스가 아니라 `number`(정수) + 함수 모듈로 옮기고, 린트 규칙으로 f64 혼입을 막는다.

포팅 비용은 크지만 불가능하지 않다. **의존 방향을 단방향으로 잡아둔 것이 이 선택지를 살려둔다.**

## 기록해두는 반론

이 문서를 읽는 사람이 "그래도 JS가 낫지 않나" 생각한다면, 그 생각은 합리적이다. 근거는 이렇다:

> 이 게임의 CPU 부하는 무시할 수준이고, 결정성은 JS에서도 규율로 달성 가능하며(실제로 많은 게임이 그렇게 한다), 번들과 빌드 복잡도는 순수 비용이다. 팀이 JS에 익숙하고 포트폴리오 목적이 없다면 **JS가 더 나은 선택이다.**

우리가 Rust를 고른 건 이 반론이 틀려서가 아니라, **포트폴리오 목적과 타입 강제의 가치를 더 크게 봤기 때문**이다. 전제가 바뀌면 결론도 바뀐다.
