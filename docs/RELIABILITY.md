# RELIABILITY.md

서버가 없으므로 "장애 대응"이 아니라 **"남의 인프라가 죽었을 때도 돌아가기"**가 신뢰성이다.

## 1. 실패 지점 목록

| # | 실패 | 확률 | 영향 | 대응 |
|---|---|---|---|---|
| F1 | Nostr 릴레이 다운 | 중 | 방 입장 불가 | 릴레이 다중 접속 + MQTT 폴백 |

## 2. 시그널링 다중화 (F1, F2)

```
접속 시도
  ├─ Nostr (Trystero 기본, 릴레이 여러 곳 동시)
  │    └─ 5초 내 피어 발견 실패 →
  ├─ MQTT (@trystero-p2p/mqtt)
  │    └─ 5초 내 실패 →
  └─ 수동 SDP 교환 UI 노출
```

- `getRelaySockets()`로 릴레이 연결 상태를 감시하고, 절반 이상 끊기면 조용히 다른 전략을 병행 시작
- `relayConfig.redundancy`를 기본값보다 높여 릴레이 여러 곳에 동시 접속
- **전환은 조용히.** 사용자는 "연결 중..."만 본다. 세 번째 단계에 가서야 화면이 바뀐다

수동 SDP 교환은 UX가 나쁘지만 **제거 대상이 아니다** (CB-5). 이 경로가 없으면 남의 인프라에 프로젝트의 생존이 걸린다.

## 3. 호스트 이양 (F4) — 가장 중요

호스트 이탈은 **흔한 일**이다. 브라우저 탭을 닫거나, 전화가 오거나, 지하철에 들어가거나.

### 선출

```
새 호스트 = 남은 피어 중 selfId 사전순 최소값
```

- 투표·합의 불필요. 모든 피어가 같은 목록을 보고 같은 답을 낸다
- 동점 없음 (`selfId`는 고유)
- 선출에 네트워크 왕복이 0회 → 즉시 재개

### 상태 복구

각 클라이언트는 마지막으로 받은 스냅샷 N개(기본 8개, ≈530ms)를 보관한다. 새 호스트는:

1. 자기가 가진 가장 최신 권위 스냅샷으로 `World`를 복원
2. 그 이후 자기 로컬 입력을 재적용
3. 다른 피어에게 `HostHandoff { new_host, resume_tick }` 브로드캐스트 (reliable 채널)
4. 피어들은 `resume_tick`으로 되감고 재개

되감기 손실 최대 2틱(≈66ms). 라운드는 이어진다.

### 알려진 한계

- 이전 호스트만 알던 정보(아직 아무에게도 안 보낸 숨은 사람 좌표)는 **복구 불가**. 새 호스트가 가진 스냅샷에는 자기 시야 정보만 있다
- 대응: 호스트는 스냅샷과 별개로, **`HostShadow` 패킷**을 2초마다 후보 호스트(사전순 2위) 한 명에게만 보낸다. 전체 월드 상태의 압축본
- 이건 "2위가 좌표를 안다"는 뜻이므로 DD-002와 긴장 관계다. **타협**: `HostShadow`는 좌표를 4타일 단위로 양자화한 저해상도 상태만 담는다. 이양 후 몇 틱이면 정확도가 회복된다

> 이 타협은 완벽하지 않다. 2위 피어가 개조 클라이언트면 4타일 정밀도의 위치를 알 수 있다. 4타일은 방 하나 크기라서 "어느 방에 있다" 정도이고, 게임을 망가뜨리는 수준은 아니라고 판단했다. 재검토 트리거: 플레이테스트에서 이걸 악용한 사례가 나오면.

## 4. 피어 끊김 (F5)

```
마지막 패킷 수신 후:
  0.3초  → "연결 불안정" 아이콘
  3초    → 캐릭터 정지, 무적 아님 (도망 못 침)
  10초   → 유령 처리, 라운드에서 제외
  재연결 → 다음 라운드부터 정상 복귀
```

**3~10초 사이에 무적을 주지 않는 이유**: 일부러 연결을 끊어서 무적이 되는 치트가 생긴다. 끊긴 사람이 손해 보는 게 맞다.

## 5. 탭 백그라운드 (F8)

브라우저는 백그라운드 탭의 `requestAnimationFrame`을 멈추거나 1Hz로 떨어뜨린다.

```
visibilitychange → hidden:
   - 렌더 중단
   - 입력 전송 중단 (움직이지 않음)
   - 스냅샷 수신은 유지 (워커 아님, 메시지 큐에 쌓임)

visibilitychange → visible:
   - 누적 스냅샷 중 최신 것만 적용, 나머지 폐기
   - 로컬 예측 버퍼 초기화
   - 렌더 재개
```

**따라잡기 상한**: 누산기 루프는 프레임당 최대 5틱까지만 진행한다. 그 이상 밀렸으면 시뮬레이션을 버리고 호스트 스냅샷으로 강제 동기화한다. death spiral(따라잡느라 더 밀리는 현상) 방지.

## 6. 관측 가능성 (서버 없이)

로그를 보낼 곳이 없다. 그래서 **게임 안에서 보여준다.**

⚙ → 디버그 패널 (기본 꺼짐):

```
FPS        58       틱          1842
RTT(호스트) 47ms     보간 버퍼    3
손실률      0.4%     재조정/초    2.1
업로드      8.6 KB/s 릴레이       nostr(3/5) ✓
```

버그 제보 시 사용자가 이 화면을 캡처해서 보낼 수 있다. 이게 우리의 텔레메트리다.

추가로 `?debug=1` 쿼리로 개발자 오버레이(히트박스, 가시성 그리드, 패킷 덤프)를 켤 수 있다. 프로덕션 빌드에도 남긴다 — 숨겨봐야 의미 없고, 있으면 제보가 좋아진다.

## 7. 테스트 전략

| 종류 | 대상 | 도구 |
|---|---|---|
| 단위 | `sim` 로직, 고정소수점, 가시성 판정 | `cargo test` (네이티브) |
| 결정성 | 같은 입력 → 같은 해시, 1000틱 | `cargo test` |
| 유출 | 비술래 아웃바운드에 좌표 없음 | `cargo test` (CI 필수) |
| 프로토콜 | 직렬화 라운드트립, 깨진 입력 fuzz | `cargo test` + `cargo fuzz` |
| 네트워크 시뮬 | 지연 80ms / 손실 5% / 지터 30ms 환경에서 플레이 가능 | 가상 전송 계층으로 헤드리스 다중 피어 |
| E2E | 실제 브라우저 2개로 방 입장 → 라운드 진행 | Playwright (Chromium) |
| 실기 | 모바일 조작·발열 | 수동. 기기 없으면 "미확인" 기록 |

**네트워크 시뮬 테스트가 핵심이다.** 로컬에서 두 탭을 띄우면 RTT가 0ms라 아무 문제도 안 보인다. 가상 전송 계층에서 지연·손실을 주입해야 진짜 버그가 나온다.
