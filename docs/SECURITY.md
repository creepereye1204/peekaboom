# SECURITY.md

서버가 없으면 해킹당할 서버도 없다. 하지만 **클라이언트가 곧 서버**이므로 위협 모델이 다르다.

---

## 1. 위협 모델

우리가 지키려는 것:

| 자산 | 위협 | 심각도 |
|---|---|---|
| 숨은 사람의 좌표 | 패킷 관찰 / 개조 클라이언트 → 월핵 | **치명** (게임이 성립 안 함) |
| 게임 결과 판정 | 클라이언트가 "안 잡혔다" 주장 | 높음 |
| 방 참가자 명단 | 시그널링 릴레이 운영자가 관찰 | 낮음 |
| 사용자 개인정보 | — | **해당 없음** (아무것도 수집/저장 안 함) |
| 인프라 | — | **해당 없음** (인프라가 없음) |

우리가 **지키지 않는 것** (명시):

- 호스트 본인의 치트 (§3)
- 트래픽 분석으로 "누가 누구와 게임 중인지" 추론
- 결정적 DoS (누군가 방에 쓰레기 패킷을 퍼붓는 것) — 완화만 함

---

## 2. 좌표 유출 방어

**핵심 방어선은 DD-002의 피어별 가시성 필터링이다.**

원칙: **클라이언트에게 안 보여줄 정보는 애초에 보내지 않는다.** 보내고 안 그리는 건 방어가 아니다.

구현 규칙:

1. 호스트는 `visible_to(peer)`를 통과한 엔티티만 직렬화한다
2. 시야 밖 근접 인기척은 **1타일 단위로 양자화**해서 보낸다
3. 소음은 방향만, 거리 없이
4. 렌더러는 받은 것만 그린다. 렌더러에 "숨김 플래그"가 있으면 안 된다

### CI 강제

`tests/no_leak.rs` — 시뮬레이션을 200틱 돌리면서 술래가 아닌 피어의 아웃바운드 버퍼를 전부 덤프하고, 숨은 플레이어의 실제 좌표(±1타일)가 등장하지 않음을 단언한다.

**이 테스트 실패 = 머지 불가.** H4는 성능이 아니라 게임 규칙이다.

## 3. 호스트 치트 — 받아들인 리스크

호스트는 전체 월드 상태를 갖는다. 호스트 클라이언트를 개조하면 모두의 위치가 보인다.

**서버 없이는 구조적으로 막을 수 없다.** 암호학적 대안(커밋먼트 스킴, zk 증명)은 DD-002 §대안A에서 검토했고 브라우저 30Hz에서 실행 불가로 기각했다.

### 완화책

| 조치 | 설명 |
|---|---|
| 호스트 공개 | 로비와 게임 중 HUD에 왕관 아이콘. 누가 심판인지 절대 숨기지 않는다 |
| 사회적 신뢰 | 방 코드를 아는 사람만 들어온다. 보통 아는 사이다 |
| 보상 없음 | 랭킹·전적·재화가 없다. 치트해서 얻는 게 없다 |
| 호스트 회피 불가 | 호스트를 못 믿겠으면 그 방을 나가면 된다. 방을 직접 만들면 자기가 호스트다 |

### 문서화 의무

README와 첫 실행 화면 어딘가에 한 줄 적는다:

> 방을 만든 사람이 심판 역할을 합니다. 모르는 사람 방에서는 공정성이 보장되지 않아요.

숨기지 않는다. **사용자가 아는 리스크는 리스크가 덜 된다.**

## 4. 악성 피어 대응

호스트가 아닌 피어가 할 수 있는 나쁜 짓과 대응:

| 공격 | 대응 |
|---|---|
| 불가능한 입력 (속도 999) | `InputIntent.move_dir`는 정규화된 방향뿐. 속도는 호스트의 `sim`이 정한다. 구조적으로 불가 |
| 입력 폭주 (틱당 1000개) | 호스트가 피어별 입력 레이트 리밋 (틱당 최대 2개, 초과분 폐기) |
| 거대 패킷 | 수신 메시지 크기 상한 4KB. 초과 시 해당 피어 연결 종료 |
| 잘못된 형식 패킷 | 파싱은 전부 `Result`. 실패 시 패킷 폐기 + 카운터 증가. 100회 초과 시 킥 |
| 채팅 스팸 | 초당 1메시지, 길이 200자 상한. 클라이언트 측 뮤트 기능 |
| 계속 재입장 | 호스트가 `selfId` 기준 킥 목록 유지 (라운드 동안만, 서버가 없어 영구 밴 불가) |

**모든 역직렬화 경로는 신뢰하지 않는 입력을 다룬다.** `crates/net/src/decode.rs`에는 `panic!`/`unwrap()`이 없어야 한다. clippy 린트로 강제.

## 5. 시그널링 릴레이에 대한 노출

공개 Nostr/MQTT 릴레이는 남의 인프라다. 릴레이 운영자가 볼 수 있는 것:

- 어떤 appId/roomId로 누가 접속을 시도했는지
- SDP (Trystero가 appId+roomId 파생 키로 암호화하지만, appId/roomId를 아는 사람은 복호화 가능)

**Trystero `password` 옵션을 쓴다.** 방 생성 시 방 코드와 별개로 랜덤 패스워드를 생성해 URL 프래그먼트에 함께 담는다.

```
#r=A7K3QX&k=<base64url 16바이트>
```

- 이러면 릴레이 운영자가 SDP를 복호화할 수 없다
- 링크를 받은 사람만 들어올 수 있다 (코드 무작위 대입도 막힌다)
- URL 프래그먼트는 **HTTP 요청에 포함되지 않는다** — GitHub의 서버 로그에도 안 남는다

게임 데이터 자체는 WebRTC DTLS로 종단간 암호화되므로 릴레이를 지나지 않는다.

## 6. 웹 표면

정적 사이트라 공격 표면이 작다. 그래도:

- **CSP 헤더** — GitHub Pages는 커스텀 헤더를 못 주므로 `<meta http-equiv="Content-Security-Policy">`로. `script-src 'self'`, `connect-src` 는 릴레이 도메인 화이트리스트 + `wss:`
- **SRI** — CDN에서 Trystero를 불러오지 않는다. **번들에 포함**한다. 서드파티 CDN 의존은 공급망 리스크이자 CB-5 위반
- **`innerHTML` 금지** — 닉네임/채팅은 `textContent`로만. XSS 경로 차단
- 외부 링크는 `rel="noopener noreferrer"`

## 7. 우리가 수집하지 않는 것

명시적으로 기록한다. 나중에 누가 추가하려 하면 이 문단을 근거로 막는다.

- 분석/애널리틱스 도구 **없음**
- 쿠키 **없음**
- 서버 로그 **없음** (서버가 없음)
- IP 주소 — WebRTC 특성상 **피어끼리는 서로의 IP를 알게 된다**. 이건 P2P의 본질적 성질이며 우리가 수집하는 게 아니다. 다만 README에 명시한다

`localStorage`에만 저장: 닉네임, 본 힌트 목록, 설정(조이스틱 방향/소리/TURN). 전부 로컬. 전송 없음.
